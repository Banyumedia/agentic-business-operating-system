# MP-02 — Integritas POS: checkout menyentuh stok dan jurnal

Status: **DONE**. Semua acceptance terbukti termasuk batas JSON yang
dinyatakan eksplisit di teks task sendiri ("kalau ternyata tidak bisa,
batasnya dicatat eksplisit, bukan diselundupkan").

## Investigasi sebelum menulis kode

Tiga temuan mengubah rencana implementasi, semuanya diverifikasi dengan
membaca kode dulu:

1. **`OrderService`/`StockService`/`JournalService` murni Eloquent** — nol
   pemanggilan `EntityRepository` di ketiganya. `CashierScreenTest` berjalan
   di driver JSON (default) seluruhnya. Ini berarti routing checkout lewat
   ketiga servis itu **bukan** penggantian drop-in — dibutuhkan jalur ganda,
   bukan satu jalur yang "hanya" dipindah.
2. **`StockService::deductStock()` tidak punya lantai stok untuk item TANPA
   `track_batches`** — hanya `deductFeFo()` (item ber-batch) yang menolak
   stok kurang; item biasa menulis `stock_movements` tanpa pernah memeriksa
   saldo, bisa jatuh negatif tanpa satu galat pun. Ditutup sebelum MP-02
   memakainya, karena checkout POS pasti memakai jalur ini untuk sebagian
   besar barang ritel.
3. **Ketidaksesuaian kapabilitas pra-ada**: efek `journal.post`
   (`WorkflowEngine::EFFECT_CAPABILITIES`) digerbang `finance.cashbook`,
   padahal seluruh menu Bagan Akun/Jurnal/Rincian Jurnal
   (`DynamicMenuRegistry`) dan teks acceptance MP-02 sendiri menyebut
   `finance.accounting`. Diverifikasi: 40/40 preset menyalakan keduanya
   sekaligus atau tidak sama sekali hari ini, jadi ini bukan regresi yang
   pernah terlihat — tapi tetap salah dan dibenahi sebelum menambah pemanggil
   kedua (checkout) yang akan mewarisi kesalahan yang sama.

## Perbaikan #2 — lantai stok item tanpa batch

`app/Services/StockService.php`: `deductStock()` untuk item tanpa
`track_batches` kini memanggil `assertSufficientUntrackedStock()` dulu —
menjumlah `stock_movements` (`in - out`) dengan `lockForUpdate()` (pola sama
dengan `deductFeFo()`), menolak `RuntimeException` **sebelum** movement
apa pun ditulis bila saldo kurang. Tiga test baru di `StockServiceTest.php`
(negatif dulu): tolak stok kurang, tolak-tanpa-sisa-movement-parsial, dan
kebalikannya (stok cukup tetap berhasil, supaya pemeriksaan ini tidak diam-diam
menolak semua orang).

## Perbaikan #3 — kapabilitas jurnal dibenahi

`WorkflowEngine::EFFECT_CAPABILITIES['journal.post']`: `finance.cashbook` →
`finance.accounting`. Satu mock di `OrderServiceTest::test_order_paid_triggers_journal_post_effect`
disesuaikan (mock lama menegaskan `enabled('finance.cashbook')` dipanggil —
sekarang `finance.accounting`). Tidak ada test lain yang menegaskan nilai
literal capability ini (yang lain hanya memeriksa
`$features->enabled($capability apa pun yang di-resolve)`), jadi perbaikan
ini aman untuk seluruh fixture yang ada.

## Desain jalur ganda

`CashierScreen::checkout()` bercabang di `config('datasource.driver')`:

- **`checkoutViaAggregate()`** — jalur JSON (D-42), **byte-identik** dengan
  kode lama (`EntityRepository::saveAggregate()`). Tidak disentuh sama
  sekali. Batas dinyatakan eksplisit di komentar kode: `stock_movements`
  dan `accounting_journals` tidak punya schema JSON (keduanya tabel SQL
  murni), jadi menutup integrasi stok+jurnal di jalur JSON butuh menulis
  ulang kedua servis untuk `EntityRepository` — di luar file target task
  ini, dicatat sebagai utang, bukan diselundupkan sebagai selesai.
- **`checkoutViaOrderService()`** — jalur Eloquent (MP-02). Satu-satunya
  yang boleh dipanggil dari sini adalah `OrderService::checkoutPos()` —
  seluruh orkestrasi (transaksi, idempotensi, urutan panggilan) hidup di
  `OrderService`, BUKAN di `CashierScreen`, karena
  `test_cashier_sources_have_no_industry_branch_or_direct_database_access`
  melarang literal akses basis data langsung di `CashierScreen.php`.

### `OrderService::checkoutPos()` — satu transaksi, semua-atau-tidak-sama-sekali

1. `createOrder()` (idempoten lewat `external_ref` yang sudah ada).
2. Bila `$order->wasRecentlyCreated === false` (replay) → **berhenti di sini**,
   kembalikan order yang sama. Stok dan jurnal tidak disentuh sama sekali
   pada replay.
3. Bila baru: set `payment_method`/`paid_at`, deduksi stok per baris lewat
   `StockService::deductStock()` (dengan `$order` sebagai `reference`
   polimorfik di `stock_movements`), lalu `postPosSalesJournal()` (akun
   `1000`/`4000`, pola identik `Workflow\Effects\JournalPost`, gerbang
   `finance.accounting`).
4. Seluruh langkah dalam SATU `DB::transaction` — gagal di titik mana pun
   (stok kurang di baris kedua, Bagan Akun belum disiapkan) membatalkan
   order **dan** seluruh mutasi stok baris sebelumnya.

## Cacat pra-ada yang ditemukan dan ditutup di jalan

`CashierScreen::authoritativeLines()` menolak harga item di jalur Eloquent
dengan pesan "Harga barang atau layanan tidak valid" — `Item::price` di-cast
`decimal:2`, dan `toArray()` Eloquent (dipakai `EloquentEntityRepository::find()`)
menyerialkannya sebagai STRING numerik (`"75000.00"`), bukan int/float,
sesuai perilaku bawaan Laravel untuk cast decimal (menghindari kehilangan
presisi float). Pemeriksaan lama (`is_int`/`is_float`) menolaknya. Ini
BUKAN cacat yang MP-02 timbulkan — ini menghalangi checkout Eloquent APA PUN
sejak awal, ditemukan justru karena MP-02 adalah pemakai pertama yang
benar-benar menjalankan checkout mode Eloquent. Perbaikan: terima juga
string numerik (`is_numeric()`), cast ke float sebelum dipakai — jalur JSON
tidak terpengaruh (selalu mengirim int/float asli).

## Utang yang diterima sadar, dicatat bukan diselundupkan

Jalur JSON (D-42) **tidak** mendapat integrasi stok+jurnal — batas ini
dinyatakan eksplisit di teks acceptance task sendiri sebagai opsi yang sah.
Menutupnya penuh membutuhkan salah satu dari: (a) menulis `StockMovement`/
`AccountingJournal` sebagai entitas JSON (schema baru, migrasi konsep
sebagian data akuntansi ke luar SQL — perubahan arsitektur besar, bukan
scope MP-02), atau (b) mewajibkan `finance.accounting`/`inventory` selalu
berjalan di mode Eloquent (keputusan produk, bukan teknis). Tidak diputuskan
di sini.
