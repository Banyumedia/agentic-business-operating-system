# TX-03 — Penegakan kunci fiskal server-side + alasan terkunci (D-74)

Branch `task/TX-03` dari `main` (`b29b979`, di atas TX-02). Menyentuh
`app/Models/BusinessIdentity.php`, `app/Services/BusinessIdentityStore.php`
(hanya menambah `fiscal_locked_at` ke array read), `app/Livewire/Settings.php`
(businessSummary), `resources/views/livewire/settings.blade.php`, dan test
fiskal. Disjoint dari lajur Hermes/lead-capture yang aktif di working tree.

## Yang ditutup

Kunci fiskal harus **menolak**, bukan sekadar UI tanpa tombol. Sebelumnya tidak
ada penegakan sama sekali; `fiscal_locked_at` dicap TX-02 tapi tak ada yang
menghormatinya.

## Yang berubah

- **`BusinessIdentity::booted()`** — hook `updating` menolak perubahan
  `tax_mode`/`price_includes_tax`/`tax_rate` bila baris **sudah** terkunci
  (`getOriginal('fiscal_locked_at') !== null`). Di lapisan model, jadi setiap
  penulis (Livewire rakitan tangan, TenantBot, command) lewat pintu yang sama —
  bukan hanya komponen Settings. Kunci relevan adalah keadaan **tersimpan**,
  supaya mencap kunci itu sendiri tetap boleh.
- **Identitas belum terkunci** (data lama sebelum TX-02, `fiscal_locked_at` null)
  **tidak** ikut terkunci diam-diam — perubahan tetap boleh sampai dikunci.
- **Field non-fiskal** (nama, alamat) tetap bisa diubah pada baris terkunci.
- **`BusinessIdentityStore::read()`** (jalur Eloquent) kini menyertakan
  `fiscal_locked_at` supaya tab Profil tahu status kunci.
- **Tab Profil** menyatakan status PPN lengkap (PKP + inklusif/eksklusif) dan,
  bila terkunci, kalimat eksplisit "Terkunci sejak pendaftaran … untuk perubahan
  yang sah (mis. usaha Anda menjadi PKP), hubungi dukungan" — keputusan yang
  disengaja, bukan fitur yang lupa dibuat.

## Keputusan yang dikunci test (negatif lebih dulu)

- Locked → ubah `tax_mode` / `price_includes_tax` / `tax_rate` ditolak
  `LogicException`.
- Unlocked → field fiskal masih boleh diubah (identitas lama tidak terkunci
  diam-diam).
- Mencap `fiscal_locked_at` pada baris unlocked → boleh.
- Locked → field non-fiskal tetap boleh.
- Tab Profil merender alasan terkunci saat locked, dan tidak saat unlocked.

## Temuan yang memblokir gate penuh (diangkat jadi task: TX-ISO)

Saat memverifikasi TX-03 saya menemukan bahwa `php vendor/phpunit/phpunit/phpunit`
**penuh** gagal tidak konsisten (15 error + 9–12 gagal) **dengan atau tanpa
perubahan TX-03** — dibuktikan dengan menjalankan suite penuh di `main` bersih
(WIP TX-03 di-stash): sama-sama merah. Setiap test yang gagal **hijau saat
diisolasi**. Akar: `JsonCompanySettingsStore::update()` menulis lewat
`Storage::disk()->path()` + `fopen`/`Filesystem::replace` native, melewati
`Storage::fake`; test yang hanya set `datasource.json_path` tanpa mem-fake disk
menulis ke `storage/app/json` nyata dan mencemari test lain (mis.
`SettingsCapabilityTabsTest` → `ContractScreenTest`: "Identitas usaha tidak
ditemukan: bengkel-arka").

**Percobaan tambal cepat sengaja dibatalkan.** Mengubah `update()` menulis lewat
`$disk->put()` menghilangkan kebocoran `settings.json`, tetapi menggeser gejala
ke asumsi `assertMissing` di test lain karena kunci flock + `read()` masih
campur native/facade. Perbaikan yang benar menuntut seluruh store konsisten
facade (termasuk lock) — itu tugas tersendiri, bukan diselundupkan ke TX-03.
Store dikembalikan ke keadaan semula; TX-03 diverifikasi lewat run terisolasi.

Ini konsisten dengan catatan lama di `AUTOPILOT_STATUS.md`: "gate yang hasilnya
berubah antar-jalankan tidak bisa dipakai sebagai gate — layak jadi task
tersendiri (isolasi disk test per proses)."
